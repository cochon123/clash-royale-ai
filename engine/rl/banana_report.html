Where the starting weights came from

The user-selected 4.4.2 checkpoint is a behavior-cloning actor trained on winner replay actions. Its recorded source dataset contains approximately 1.48 million action samples from 50,918 decisive replays. Its roughly 967,000 parameters include a two-layer recurrent model with width 160, a 64-event context, three internal thinking steps, and a card-conditioned placement heatmap. Those are inherited training data; the counters above count only new native matches in this run.

The original engine connection

The deck runner executes the recovered original ARM64 engine through Unicorn. It modifies the original scenario's deck configuration inputs, then calls the game's original input and harness constructors to build a fresh battle. Every reset reads back all eight native source card rows for both sides. Card selection, placement validation, mana checks, command submission, combat, and the terminal winner come from original routines.

The current Rust static recompilation has exact validation on the older prepared scenario. This run uses the original runtime for fresh specialized decks while that broader recompilation coverage is unfinished. The dashboard identifies the runtime used.

The observation adapter is still limited.

The policy sees its deck, current hand, elixir, and the causal history of accepted card plays. It does not yet see troop positions, troop HP, or tower HP. Therefore this experiment measures learning with a partial observation. It does not establish tactical strength or equivalence to a full native game-playing client.

Learning objective and method

Only original-engine terminal outcomes earn reward: +1 for a win, −1 for a loss, and 0 for a draw. Truncated or interrupted games produce no invented winner and no terminal-reward update. The actor is warm-started; a small value head and a state-conditioned wait gate are newly initialized.

PPO uses a clipped probability ratio of 0.2, learning rate 0.00003, two passes per rollout, and minibatches of 32. The rollout stores detached inputs and the sampled placement candidate set so later probability calculations use the same action support. Native hands and elixir constrain card choices. Rejected deployments remain rejected; only accepted card plays enter subsequent action history.

The terminal reward keeps its sign in the advantage calculation. Centering all advantages from a single game would cancel that game's constant win/loss signal, so this trainer avoids that error. The inherited deterministic sub-tile offset can drift as shared features change. Its likelihood is not modeled explicitly, so this is an approximate PPO adapter for the full coordinate action; card, placement tile, and wait probabilities are optimized explicitly.

Reading the dashboard

The main curve is the rolling score against the frozen starting policy over the last 20 training games (wins count 1, draws ½). The model cards show strict wins divided by completed training games. Separate deterministic evaluations help distinguish sampling behavior from policy progress. Small samples and different deck matchups do not support a reliable strength ranking.

Quickest and longest matches, streaks, most deployed card, and spent elixir come from accepted native actions and completed outcomes. The raw log records work done and the remaining time. Empty metrics stay empty until real data exists.

Compute, files, and stopping

Local machine: NVIDIA RTX 3050 Laptop GPU with 6 GB VRAM, Intel Core i5-13420H, and 32 GB system RAM. PyTorch uses CUDA for policy work; original engine execution runs on the CPU. The two specialists alternate matches within the shared budget.

Run folder: runs/banana-league-20261019. It contains state.json, progress.jsonl, train.log, initial weights, and atomic current checkpoints for both specialists. Checkpoints include model names, deck lists, source identity, configuration, value and wait heads, and optimizer state.

The dashboard's Stop & save button creates a stop marker. The trainer saves both policies and reports stopped status. The deadline follows the same save path. Closing this browser does not stop the systemd-managed run. No cloud training or external API key is used.

What we can learn from this run

This first experiment can establish real throughput, deployment acceptance, stable updates, and whether win rates change against a fixed starting opponent. A weak result could come from partial observations, placement constraints, sparse rewards, or limited game diversity. Logs and checkpoint provenance allow those causes to be investigated before spending time on a larger run. No improvement is claimed until actual results support it.
