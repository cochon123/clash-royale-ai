01

What exists today

The short answer to the questions that caused confusion.

The original game engine runs. The full Rust combat rewrite is unfinished.

The current system executes the supplied game's compiled ARM64 engine in Unicorn, with a Rust host controlling it and a Python Gymnasium environment above it. We have decompiled selected functions and recovered contracts. We do not have the complete original C/C++ source tree.

Working now

  • Headless matches using the original native test harness and its built-in bots.
  • External card commands through original native validation and deployment.
  • A persistent Python reset()/step(action) interface with a simple external opponent.
  • Partial structured observations and native win/loss/draw rewards.
  • A measured end-to-end games-per-minute benchmark.

Still separate work

  • A playable desktop battle with the original graphics, HUD and interactive human controls.
  • Arbitrary decks, famous presets and integration of the user's trained AI agents into this native path.
  • Unit positions, unit health and tower health in the RL observations.
  • A faithful Rust implementation of the complete combat simulation.
  • A phone release and an original-client-compatible offline server.

The new RL prototype is usable for integration and throughput experiments. No neural-network policy was trained as part of this work. Its benchmark uses two simple affordable-card/random-position Python policies. E25 E27 E31

02

How the pieces fit together

Original battle code at the bottom; newly written control layers above it.

  1. Python policyAgent + simple opponent

    Choose wait/card/position actions. No built-in bot decisions are invoked by these RL transitions.

  2. Python adapterGymnasium environment

    Numeric observations, action conversion, sparse rewards, reset/step and episode caps.

  3. Rust adapterPersistent native session

    JSON-lines requests, hash-verified snapshot restore and calls into original functions.

  4. Execution dependencyUnicorn ARM64 emulator

    Executes the original instructions on this x86-64 desktop with explicit imported-function models.

  5. Original gameDecoded libg + native resources

    World updates, card validation, commands, entities, deployment and finalized match outcome.

The original-resource UI viewer is a parallel component. Its asset playback is validated independently, but it is not connected to this battle loop. The earlier approximate Rust simulator is another separate component and is not used by the native RL environment. E04 E30

Why keep a reference execution path?

A faithful Rust port needs something authoritative to compare against. Executing the original instructions supplies a reference for recovered operations. The current Python/Rust comparisons establish that two execution adapters agree for specific native workloads; they do not yet compare a full Rust combat implementation against the original.

Two kinds of AI vs AI, with different workloads

Original harness: original function 11d6364 repeatedly calls the original bot/harness update. This path includes extra testing, serialization and validation work.

RL loop: external Python policies submit card commands, then the Rust session advances the original world function. The builtin bot loop is not called. The trajectories, decisions and overhead differ, so the old warm harness timing and the new RL benchmark are not directly comparable speedups. E13 E25

03

Goal and change of direction

The desktop goal stayed the same; the first independent simulation did not meet the fidelity requirement.

The requested destination is a desktop game with human vs AI and AI vs AI, per-side controller selection, eight-card decks or familiar presets, direct battle launch, the original Clash interface, and a fast headless engine for possible reinforcement learning. Android is a later target.

An earlier implementation provided a playable local Rust simulation, browser arena, deck selection and an AI-policy bridge. It consumed extracted game data and original card pictures, but approximated movement, targeting, spells and many special mechanics. The user explicitly rejected that as the intended solution. It remains under src/, web/ and run.sh as a separate prototype. E30 E02

The subsequent work concentrated on the supplied native binary: decrypt it, execute its actual constructors and resource loading, recover battle and input contracts, and establish native runtime evidence. The most recent scope was deliberately narrower: make the simplest usable RL interface first and measure it before committing to the full Rust rewrite.

No project-completion percentage is asserted. Earlier “points” estimates were planning judgments, not measured progress. A working native reference and a minimal RL wrapper are major milestones; neither establishes a nearly finished native desktop client or combat rewrite.

What was retained from the earlier effort

Package extraction, source hashes, resource catalogs, card art and analysis tools remain useful. The old model's rules, UI and very high throughput are not evidence of original-engine equivalence and are not substituted into the new RL runtime.

05

Recovering the original assets and data

This supplied usable source material without pretending that configuration files contain the entire engine.

Resource and card-data extraction

All 645 packaged CSV/TOML resources were decoded, with packaged and decoded hashes and size/encoding checks. The catalog retains 375 raw card variants and 153 base-card entries, together with character, building, projectile, area-effect, buff and extension records. Original PNG card art was copied unchanged. Blank-name continuation rows and unused/event variants were retained in the raw catalog rather than silently collapsed. Package presence does not prove live availability. E03 E02

Original UI structure

Six selected SC5 display documents were decoded: the main UI, ability button, deck builder, spectator HUD, battle-end UI and arena UI. Recovery preserves child names, named exports, polygons, UVs, transforms, colors, masks, text metadata and frame labels. Atlas textures and six bundled TrueType fonts were retained. The main ui.sc contains 3,087 shapes, 4,871 movie clips, 2,695 text fields and 2,079 named exports. E04

Two upstream-parser mismatches had to be corrected: string indices needed direct zero-based lookup, and SCTX pixel type 208 required ASTC RGBA 6×6 decoding. Those corrections were checked against pinned primary upstream readers. Other selected atlases use ASTC 8×8.

A separate Rust display-list renderer reads the recovered trees and atlas PNGs. It traverses original clip frames, applies matrices/colors, rasterizes triangle strips and composites masks/blend modes. All 56 sampled states match an independent corrected Python parser/rasterizer pixel for pixel, including image origin: player and spectator HUDs, two mask-bearing components, and all 52 ability-button root frames. The authored ability timeline has 52 frames at 30 FPS. E05

SCDB schemas and original logic graphs

The asset database is SQLite. Its 162 UI-schema and 155 UI-timeline blobs decode as JSON. Separately, 2,458 original logic/animation JSON assets were recovered. Important scope separation: all 509 game-object flows, 176 player flows and six behavior FSM assets in the identified flow families belong to logic/autochess/, associated with Merge Tactics. They are not recovered ordinary Royale troop AI. Another 477 chaos-data assets provide Royale extension configurations, while the native handlers remain essential. E06

Asset recovery is one layer of the client. Original text layout, resizing, state selection, game bindings, the battlefield renderer and interactive controls are not established by successful asset decoding or reference raster matches.
06

Making the native engine readable

The protected engine first had to become analyzable machine code.

The original ARM64 libg.so contains protected executable ranges and strings. Early decompilation only exposed an initializer thunk, which was insufficient to recover combat. The initializer relies on the companion libsupercell_clashroyale.so. An isolated Android startup capture supplied relocated companion memory for controlled execution. E07 E02

  1. Recover the companion's protected text. Executing its original routine at RVA 0x65bb90 changed 4,841,564 bytes inside a 4,860,456-byte region. This exposed the loader callbacks and binding-codec path.
  2. Recover the binding metadata. The signed-envelope asset contains 416 protected bindings. Original codec execution recovered the exact 672-byte metadata requested by libg; a later audit ties all 416 records to retained original decoder outputs. The envelope signature itself was not verified.
  3. Execute and translate the real loader. Bounded control-flow recovery and instruction translation made its arithmetic practical to verify. Native checkpoints were compared across scalar/vector registers, flags and mapped memory.
  4. Implement the recovered cipher in Rust. Speck64/128-CBC with 27 expanded round keys reproduced the original loader's inverse operations and CBC chaining. Source and metadata hashes are checked before output.
  5. Verify all five ranges. The Rust decoder's 19,190,488 output bytes match completed original native loader execution, with zero range differences.

The resulting analysis ELF retains the original layout and relocation slots and makes native entry points, parsers, battle functions and UI binding code readable. This is recovered machine code; it is not the original C++ source tree. E09 E08

Analysis intervention and the meaning of the decryption timing

The captured companion had not completed initialization: its metadata tree was empty. The adapter supplied independently recovered original decoded bytes at the verified metadata lookup boundary. That intervention is recorded; it does not claim a successful unmodified Android startup.

The Rust decoder processed the protected ranges in approximately 0.0813 seconds in a retained run. That measures decryption and output hashing. It does not measure battle speed, Rust combat speed or RL throughput.

The loader translation is a separate verification/acceleration artifact. Its generated C++ instruction-level implementation is not a recovered C version of the whole game. E07

07

Bootstrapping a real native battle

Native code needs correctly initialized data, services and objects before a tick is meaningful.

After decoding, focused analysis used original unwind/FDE bounds, exact instruction bytes and source hashes. Ghidra display addresses include a 0x100000 image base; report RVAs below exclude it. ARM64 hidden structure returns through X8 were checked against assembly rather than guessed from decompiler argument order. E10

Native loading chain

  1. Global constructors. Execute all 763 original game constructors, together with the required packaged C++ and Sentry constructor paths. Sentry code is a dependency here; telemetry delivery was not initialized.
  2. Outer context and asset service. The bare context factory leaves a required asset holder absent. The original outer manager route initializes the context and holder used by later native jobs.
  3. Original parsers and tables. Original CSV/TOML/JSON functions parse the bytes and construct original native rows. Preparation covers 164 nonnull tables; localization and flag-1 typed postload establish cross-table references and cached records.
  4. Original SCDB types and prefabs. Explicit original type registrars and filesystem-provider setup allow the native SQLite and prefab machinery to read the 23,543,808-byte database. A real projectile-prefab lookup succeeds.
  5. Original object factory and services. A bounded source-hashed startup instruction region installs original factory providers. The CSV-loader service selects its supported synchronous (0,0) configuration for this offline execution.
  6. Maps and battle construction. All 209 Location map loads from 202 original CSVs complete. The native Normal harness constructs configuration, decks, world, battle, command manager, arena, tilemap and initial objects.

The completed chain is retained in analysis/native-pipeline/battle-full-04/. Its prepared battle contains six native entities and 18 nonnull components. The audited entity/component tick callbacks point into executable regions of the original engine. Empty objects or fabricated vtables were not used to claim battle success. E11 E12 E14

OS and runtime models needed to get there

Files, imports and time

Read-only, hash-bound virtual files and mappings supply real bytes. Native SQLite and parsers still execute. Observed allocation, memory, string, formatting, clock and selected Android/Bionic calls are modeled explicitly. Unknown imports/conversions stop execution.

Workers, TLS and allocation

Cooperative ARM64 workers execute original job callbacks with separate stacks, TLS, mutex ownership, condition waits and saved contexts. A reusable aligned guest heap replaces the insufficient bump-only analysis allocator.

Important modeling choices and limitations
  • The model reports 4 KiB pages and one configured/online virtual processor using Android's actual sysconf constants. A prior page-size response to a CPU-count query was corrected, and affected loading was replayed.
  • The clock is deterministic: supported query results advance by a fixed virtual amount. Native performance and original phone OS timing are not reproduced.
  • The read-only asset boundary returns missing only after verifying absence in all supplied APK splits. Present assets needing an unsupported AAsset API cause explicit failure.
  • The original 256 MiB analysis heap was expanded with allocation reuse and support for additional arenas. Retained bootstrap snapshots include legacy allocation bookkeeping; that count is not a measurement of the original game's live RAM requirement.
  • Busy-wait preemption, timed waits and full TLS-destructor teardown are not a complete modeled Android threading runtime.
  • Bounded startup-region execution, recovered metadata lookup and the chosen offline service settings are explicit analysis interventions. No complete Android runtime-equivalence claim follows.

Native setters provide its card and coordinates; the original submit helper attaches the actor/current tick, validates it and queues it.

Checkpoint and replay boundaries

Checkpoints bind original source, saved memory, imports, allocation metadata, register state and supporting runtime information. The Rust adapter verifies the exact Unicorn shared-library identity and restores architectural registers rather than treating an opaque serialized CPU-context blob as a portable public ABI.

In two original native replays the opaque Unicorn CPU-context byte strings differ, while every architectural register and saved memory-region hash agrees. The report therefore states architectural/state equality and separately records the opaque-context difference. It does not claim the opaque blobs are identical. E15

Corrections that matter to interpretation
  • Decompiler addresses: Ghidra's image base must be subtracted arithmetically; an early hand-slot getter candidate was corrected to raw RVA 0xf9dd98.
  • Hidden return buffers: ARM64 X8 structure-return destinations are not ordinary first parameters. Putting scratch storage below SP can overlap a callee frame; proper allocated storage is used.
  • Descriptor vs proxy: d77c8c receives the selection descriptor; e80680's proxy is for placement checks.
  • Native row identity: the global-ID getter uses offset 0x40, not decimal 40. A real Mortar ID/name/cost assertion covers this.
  • Formatted text vs actual error: the harness formats a card-event “too many” message before testing whether count exceeds 4,096. Formatting-call counts are not failure counts. The same applies to the pointer-identity message constructed before a pointer comparison.
  • Winner vs terminal event: event code 0 means the completion route; winner is a separate signed field. Equal cached side counts do not establish a draw.

The minimal reinforcement-learning environment

The new deliverable: a real reset/step loop around the recovered engine.

Session and protocol

NativeSession owns the Unicorn instance and stable boxed API/hook state. It restores the original snapshot once per reset, then keeps the process and engine alive between steps. A single reusable descriptor scratch allocation avoids allocating one for every observed hand card. Session methods expose native world stepping, hand observations, card submission, completion and an optional original-harness reference call.

The native-rl executable accepts sequential JSON lines: reset, step, observe and close. Actions for both sides are parsed before execution; at most one action per side is accepted per decision step. Native execution failures discard the session and require reset. The adapter does not silently substitute an approximate engine or fabricate success. E25 E31

Opponent, reset and episode semantics

The controlled agent is side 0. The default opponent is a simple Python policy selecting affordable cards and random positions for side 1; an optional wait opponent submits no cards. Default action spacing is 20 original world ticks. There is no real-time rendering pace.

reset(seed=...) seeds Python sampling. The native engine resets to the same prepared tick-2 snapshot with the same native RNG state and decks. Different Python seeds produce different action trajectories; they do not randomize the engine's underlying initial scenario.

Default episode cap is 7,200 native ticks. A genuine completion sets terminated=True. Reaching the cap first sets truncated=True and returns zero reward; it is not counted as a completed game. Further steps require reset. E25 E26

Reward recovered from the original finalizer

The original finalization routine d3e360 sets completion at battle+0x1e0 and stores a signed result at battle+0x1b8: 0 means side 0 wins, 1 means side 1 wins, and −1 means draw. Native later player lookup reads this same field. The wrapper reads it only after completion and rejects unsupported values. Side 0 receives +1, −1 or 0 accordingly; before completion reward is zero. Android lab results

The x86-64 Android lab accepted the ARM64 APK split through Android's native bridge but exited during protection startup before libg was mapped; the exact cause is unresolved. A separate ARM64 QEMU system booted and launched unchanged APK splits, but the protection companion's JNI_OnLoad returned JNI_ERR before loading libg. The large asset pack was not yet installed in that separate baseline lab. No successful phone/client startup is claimed. E29

Practical continuation order

  1. Improve observations. Recover native unit identity/team, position, health and tower state to give an agent meaningful combat feedback.
  2. Make initial conditions configurable. Safely expose native deck and scenario initialization, plus engine RNG variation, without fabricated row layouts.
  3. Profile the existing runtime. Investigate snapshot reload and interface costs, then measure before and after. Parallelism and reset changes require their own correctness checks.
  4. Connect controllers and presentation. Integrate desired policies and original UI/battle rendering for a genuinely playable desktop client.
  5. Port combat components to Rust progressively. Use original execution as the reference, with meaningful deterministic and edge-case comparisons, before making a performance/fidelity claim.

No official account or live online match was used for these tests. The current evidence is local offline execution of supplied artifacts. Broad parity with the full official client, all cards, all game modes and all Android/runtime behavior remains unestablished.

Reading the evidence correctly

Older ledgers retain historical status and failed or superseded attempts. This consolidated report uses later successful runs where explicitly cited. A source hash establishes the artifact used; a successful probe establishes the exercised behavior. Neither automatically establishes behavior of untested cards, modes, native branches, original client graphics or a future Rust port.

XAPK / APK
The supplied Android package bundle and its split archives.
ELF / ARM64
The native library format and instruction architecture of the shipped engine.
RVA / FDE
Relative virtual address and unwind-defined original function extent, used to anchor analysis.
Oracle / adapter parity
Original execution used as a reference; matching control adapters are different from matching a rewritten combat engine.
Native tick
One original world-counter update; benchmark counts it directly rather than pacing a rendered client.
Termination / truncation
Engine-completed outcome versus an external episode cap; only native completions count as completed games here.
